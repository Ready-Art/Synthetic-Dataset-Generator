# 📝 Changelog — v13.x

Newest first. [v12](changelog-v12.md) holds the rest of the history.

### v13.5.2
- **Fixed: the exit beat was narrated twice** — the man's message and the assistant's reply both performed the same departure, back to back. The man wrote *"I forgot the delivery window for the depot, I am so sorry, I have to go!"* and the assistant's very next reply repeated it almost verbatim. **Why:** the v13.5.1 cast-note fix gave the man the note for the **next assistant slot** so he would know who was in the room — but that note carries the `LEAVES` / `ARRIVES` **directive**, and the assistant reply for the same slot is given the same directive, so both sides obeyed it. **Fix:** `_cast_presence_note()` gained a `transitions` argument. With `transitions=False` it emits only the `PRESENT` / `NOT IN THE SCENE` lines and drops every `LEAVES` / `ARRIVES` / `CUT-AWAY` directive. Both of the man's call sites now pass it, so he still learns who is present — which is what the v13.5.1 fix needed — but only the assistant narrates the beat. Presence-only is stable by construction, so the prefix cache is unaffected. Verified over a 6-task run: the assistant still narrates departures (*"She exited the room and shoved the heavy mahogany door shut"*), the man now only reacts to them (*"The coward leaves us to our own devices"*), and no row repeats a beat
- **New: `detection.foreign_word` catches a word from another language written in Latin letters** — the `non_latin` check is a Unicode **script** allow-list, so it cannot see `green olhos`, `brown ojos`, `green ogen` or `blue expires`: every character is plain Latin and the check passes them. A phrase list cannot catch them either, because there is no fixed phrase — only a word in the wrong language. The new check is **word based** and deliberately conservative: it flags only words with **no English homograph**, so it never rejects a good reply and burns a regeneration on it. Words that are also ordinary English (`pie`, `sole`, `hay`, `sea`, `come`, `dice`, `son`) are deliberately not listed. It also catches two words fused with a capital in the middle (`visiblyTrembling`, `blueEyes`), with an allow-list for real camel-case names and brands (`iPhone`, `JavaScript`, `McDonald`), and — when given the cast — a character name fused to the next word with no capital at all (`Jessieshifted`). No LLM call, no network request, no phrase list
- **A corruption that collides with a real English word is deliberately NOT caught** — `expires` was seen once as a mangled `ojos`, but it is also an ordinary English verb (*"the contract expires"*), so flagging it would reject good replies. A false positive costs a whole regeneration, so the check stays silent rather than guess. This is documented in `detection.py` next to the word lists
- **The check is opt-in and off by default** — `detection.foreign_word.enabled` ships `false`, so a default run is byte-identical. When it fires it counts, records a recent-list entry and retries the reply with `DEFAULT_FOREIGN_WORD_FIX` appended to the system prompt, exactly like the `non_latin` ladder, and gives up after the fix list is exhausted rather than looping
- **New counters** — `app_state.foreign_word_count_total`, `foreign_word_counts_per_api`, `recent_foreign_word_total` and `recent_foreign_word_per_api`, so the dashboard's metric card, issue panel and graph can read it the same way they read every other check
- **Version bumped to v13.5.2** — a **patch** bump: two bug fixes to an opt-in feature, with no new required config key
### v13.5.1
- **Fixed: the `SCENE CAST` note leaked into saved messages** — `prompts.scene_cast` appends a per-reply cast note to the reply's final user message (or its system prompt, on `placement: system`), and some models echo it back as the **first line of the reply** instead of writing prose, so a saved message opened with `SCENE CAST` / `Samara: PRESENT` / `Ashlyn: LEAVES` / `Sage: PRESENT` above the actual scene. The echo was also **stale**: it is the note for the reply being written, so a row that kept it repeated `Ashlyn: LEAVES` on every later turn, long after she had left. New `text_utils.strip_scene_cast_leak()` is the same conservative guard as the v13.2.1 `{style}` one — it only considers the **first non-empty line**, it must be the `SCENE CAST` header itself, the block is consumed for as long as the following lines still read as cast entries (either shipped shape: `NAME: PRESENT` one per line, or `PRESENT: a, b` / `NOT IN THE SCENE: c` / `LEAVES:` / `ARRIVES:`), a blank line ends it, and a message that is ONLY the block is left alone because that is a failed generation, not a leak with prose after it. Called on the man's two message paths, each gated so a cast-free run is byte-identical. Guarded by `tests/test_scene_cast_leak_guard.py`
- **Fixed: a character was written as present, then "arrived" later** — the man's opening message is generated by the question prompt, which carried **no cast note at all**, so he wrote every character as present (touching a character the plan had marked absent). The first answer then had to narrate an arrival for someone he had already been touching. The question prompt now gets the **slot-1 cast note**, built directly rather than through `slot_notes(1)` because that also carries the persona and the woman's emotional state, neither of which belongs on the man's message. Safe at slot 1: the plan clamps a join to at least slot 2, so slot 1 never emits an arrival directive
- **Fixed: the man's later messages did not know who was in the scene** — `generate_user_continuation()` was passed only `USER EMOTIONAL STATE`, so he could address a character who had already left. The cast note for the **next** assistant slot is now appended, **last** in the concatenation, matching `slot_notes()`'s documented ordering (the final thing the model reads is who may speak)
- **Fixed: the `{style}` opener was applied to EVERY assistant reply, not just the first** — the answer prompt's `OPENING ... begin it as follows: {style}` clause was obeyed on every turn, producing a string of filler openers that read the same across rows, and the occasional incoherent cutaway into a stranger's room. The style is now passed only on the first assistant slot (`style=task_style if turn_num == 0 else ""`), and the man's continuation never carries one at all because his opening message is the question prompt. An empty style already resolves to nothing, so `fill_answer_prompt()`'s signature and `ANSWER_PROMPT_NATIVE_VARIABLES` are unchanged. The prompt text is untouched: its "if you have already replied, ignore that instruction" line is the harmless belt-and-braces half of the fix
- **Fixed: every row's exit was the same beat** — `_cast_presence_note()` picked its guidance with `(slot_no - 1) % len(...)`, and every row of a run has the same `num_turns`, so the exit landed on the same slot number in every row and every row's exit was the same shape: the character checks her phone, takes a work call, and leaves. The index now also carries a **per-task offset** derived from the task id, so two rows with the same slot count get different guidance. The offset is constant for the whole task, so two static slots still produce byte-identical notes and the prefix cache is unaffected. `config/config.yml` also now ships **8 exit and 6 arrival entries**, deliberately different in kind (a stated reason, a silent exit, an interruption from outside, a goal met, a third party sending her away, an angry exit) rather than six ways of saying "she has an errand"
- **`allow_cutaway` ships `false`** — when on, it produced disconnected filler rather than a scene: replies opening on a stray dog barking at a truck, a stray cat in a courtyard, or a stranger asleep in a basement suite. The join/leave feature works without it, and the docs now say so
- **Fixed: the headless controller crashed on a refusal-phrase hit** — `detection.issue_timestamps` and `detection.issue_timestamps_lock` are module globals initialised to `None` and wired up by **`generate.py` at module scope only**, which the control layer must never import (it builds the Tk UI). Any refusal-phrase hit in a headless run therefore died inside `detection.is_refusal()` with `'NoneType' object does not support the context manager protocol` and killed the turn. `control.py` now does the same two assignments at module scope, from the same `app_state` the controller already owns. This was a genuine pre-existing bug in the headless path, unrelated to the prompt work
- **New tests** — `tests/test_scene_cast_leak_guard.py` covers both block shapes, the block-only refusal, a block that is not first, prose that merely mentions the scene cast, byte-identical text without a block, both gated call sites in `generation.py`, and the per-task guidance offset (including that it keeps two static slots byte-identical)
- **No prompt-wording change** — the shipped prompts are untouched; the fixes are in the code that fills and cleans them, plus the two scene-cast guidance lists. The feature still ships **off** (`prompts.scene_cast.enabled: false`), so a default run is byte-identical
- **Version bumped to v13.5.1** — a **patch** bump: bug fixes to an opt-in feature plus one headless-path crash, with no new required config key
### v13.5.0
- **Fixed: the 📊 Metrics tab was slow and its figures were unreliable** — the poller ran every **10 s**, which is far too coarse for a 40-thread run: several requests finish between two polls, so a burst of bans landed as one tall spike, a short stall vanished between samples entirely, and the graphs were a handful of points joined by straight lines. The interval is now **2 s**, and the history ring grew from 120 samples to **300** (10 minutes at the new rate, and far denser than the old 20 minutes)
- **Fixed: one slow or dead endpoint delayed every other endpoint's sample** — `poll_once()` fetched the endpoints **serially**, so with a 1.5 s timeout and four endpoints one bad host could push every later sample up to 6 s late. That skew is what made figures look "missing" and made the rates wrong, because a rate is a delta over an interval. The endpoints are now fetched **concurrently**, one short-lived thread each, so a cycle takes as long as the **slowest** endpoint rather than the sum of all of them. Measured: 3 hosts that each take 0.5 s now complete in 0.50 s instead of 1.50 s, pinned by a test that fails on a serial implementation
- **`REQUEST_TIMEOUT_SECONDS` is now 1.5 s, below the poll interval** — a timeout longer than the interval would let one dead host delay the next cycle as well as this one
- **New: the metrics history is saved to `output/metrics_history.json`, ON by default** — the figures now survive the window closing. Before this, closing the generator threw away every sample, so a user who wanted to know why a run slowed down had to have had the tab open at the time. The file is a plain JSON document (readable with `jq` or a notebook) holding every endpoint's history ring, every slot's throughput ring and the per-slot token totals. `metrics.save_history: false` turns it off for a read-only or network filesystem
- **The save is atomic and throttled** — the document goes to a temp file and is swapped in with `os.replace()`, so a crash or a kill mid-write leaves the previous good file rather than a truncated one. It is written every **30 s** (`SAVE_INTERVAL_SECONDS`), not every 2 s poll: rewriting a few hundred KB on every poll is pointless churn on an SD card, and telemetry only needs to survive a restart. `stop_polling()` forces a final save, so closing the window never loses the last interval to the throttle
- **The saved document is rounded and drops `null` keys** — a `repr(float)` rate is ~18 characters and three decimals is far more precision than a graph can show; a plain-vLLM sample also carried seven `antislop_*` keys that were all `null`. Together that halves the file (237 KB → 122 KB at full history). Nothing is turned into `0.0`, so "this endpoint does not report that figure" stays distinguishable from "it reported zero"
- **Fixed: the graphs skipped every other sample** — `_VLLM_GRAPH_REDRAW_MIN_INTERVAL` was 5 s against a 10 s poll, which was fine, but against the new 2 s poll it would have dropped two samples in three. It is now 1.0 s: long enough to absorb the 500 ms UI tick, short enough to draw every poll
- **The poller runs whether or not the tab is open** — this was already true of the collection, but the tab's own refresh was gated on visibility, so switching to it showed an empty canvas until the next poll. The gate is now on the **redraw** only: `_on_dashboard_tab_changed()` still forces one on the way in, and the history that accumulated while you were elsewhere is what it draws
- **The status line names the save file and shows the real interval** — it printed `int(POLL_INTERVAL_SECONDS)`, which would silently truncate a fractional interval; it now prints one decimal and appends "History is saved to `output/metrics_history.json`"
- **New tests** — `tests/test_vllm_metrics.py` gains 15 checks (66 total): the poll interval is short enough to be usable and the timeout stays below it, the history window is dense enough to read a trend, **one slow endpoint does not delay the others** (fails on a serial implementation), saving is on by default and can be switched off, a poll cycle writes the file, the history restores after a restart, a missing figure stays missing rather than becoming zero, saving is throttled but can be forced, a corrupt or wrong-version file does not stop startup, the document is rounded and drops nulls, `stop_polling()` writes a final snapshot, the path follows `output/`, and `start_polling()` loads the saved history. `tests/test_metrics_tab_ui.py` gains 4 checks (32 total): the poller collects while the tab is closed, the status line names the save file and shows the real interval, and the graph redraw floor is shorter than the poll interval
- **No prompt, request-payload, output-row or scoring-policy change** — this only changes how often an existing endpoint is read and where its history is written. `output/` is gitignored local run data
- **Version bumped to v13.5.0** — a **minor** bump: a user-visible behaviour change (the save) plus two reliability fixes, with no new required config key

### v13.4.0
- **Overhauled: the 📊 Metrics tab is now readable and usable at a glance** — v13.3.0 put the proxy's figures into the same flat table as the vLLM ones, which meant the only way to answer "is this run healthy?" was to read a 22-column row. The tab is now, top to bottom: the status line, a **four-card KPI strip**, the per-slot table, and **four graph panels** in their own scroll region
- **New: a four-card KPI strip above the table** — **⚡ Proxy Throughput** (the proxy's own generation tokens/second), **🔥 Busiest Endpoint** (the worst KV-cache load, colour-coded by `describe_load()`), **🛡️ Bans Fired** (with the percentage the back-track fixed) and **⚠️ Errors** (upstream failures + non-2xx requests + unreachable endpoints). Each card is a big number plus one line of context, so a bare `62%` never appears without "busiest of 2 endpoint(s)" beside it. The strip is the ONE place the tab aggregates, and it aggregates the **proxy's** counters, not the vLLM server figures — the per-slot rule exists so a user can see *which* endpoint is slow, and a proxy-wide total answers a different question. It is **deduplicated by `metrics_url`**: two slots on one proxy report the same counters, so summing per row would double them (pinned by a test)
- **New: three more graph panels, each answering one question** — the v13.1.0 figure answered "which endpoint is slow and how full is its KV cache?". Three questions it could not answer now have their own panel rather than another line on a crowded axis:
  - **This Slot's Achieved Throughput** — each slot's OWN measured throughput, one line per slot. This is the figure the server cannot provide: vLLM's `/metrics` has no caller label, so two slots on one server are indistinguishable there. It needed a new per-slot history ring (`vllm_metrics.record_slot_history()`, `slot_history()`, `reset_slot_history()`), kept **apart** from the per-URL history because two slots can share one URL and would otherwise overwrite each other's line
  - **antislop-vllm-fork Proxy Activity** — requests per minute, and bans and back-tracks per minute. The request counter is cumulative, so its rate comes from the delta between consecutive samples over the wall clock between them (`_rate_history()`), the same rule the proxy's generation speed uses. A proxied slot with no bans in the window draws an explicit "that is the healthy case" note rather than an empty axes that reads as broken
  - **Requests Running vs Waiting per Server** — the panel that explains a slow generation: a high `waiting` line with a flat `running` one means the server is queueing, so the bottleneck is admission, not the GPU
- **Fixed: the table's scrollbars were too narrow to grab** — the superhero theme draws a ~10px trough with a ~6px thumb, which is unusable with a mouse on a 22-column table: the user could not drag it at all. `_grid_scrollable_table(..., wide_scrollbars=True)` now uses explicit `tk.Scrollbar` widgets with a 20px grab width, a visible trough and a hover highlight, and adds padding so the bars are not flush against the cells. The other tables are unchanged
- **Fixed: the proxy's columns now show themselves when a slot actually serves them** — the single most confusing thing about v13.3.0 was "I pointed a slot at the fork and saw nothing": the data was arriving and the columns were hidden behind an opt-in key that a shipped `config.yml` does not gain automatically (the loader does not merge new keys into an existing file). `_apply_metrics_columns()` now takes the polled rows and shows the columns when **any** row reports `antislop:` metrics, whether or not `metrics.antislop_columns` is set. The key still decides for a plain vLLM, so a default run's tab is unchanged — pinned by two tests, one for each direction
- **New: the proxy's full metric set is read, not four of twelve** — v13.3.0 read `requests_total`, `ban_events_total`, `upstream_errors_total` and `generation_tokens_total`. `summarise_antislop()` now also reads `requests_in_flight`, `request_duration_seconds` (sum + count), `streaming_requests_total`, `generations_total`, `prompt_tokens_total`, `backtracks_total` and `upstream_metrics_scrape_total` (both results) plus the last-scrape timestamp, and keeps the **per-label series** (`requests_by_status`, `bans_by_validator`, `generations_by_finish`, `streaming_by_stream`) because those are what a user tunes against. `compute_antislop_rates()` gains `ban_rate`, `backtrack_rate` and `avg_request_seconds`, all from deltas so a restarted proxy drops the sample instead of spiking
- **New: the table grew from 14 columns to 22, grouped by the request's own path** — the vLLM server figures first, then the proxy's traffic, then its ban/back-track loop, then its failures. The v13.3.0 headings are all still there (`Proxy Requests`, `Bans (fixed/total)`, `Proxy Errors`, `Proxy Gen Speed`), so a saved screenshot or a user's muscle memory still finds them; the new ones are `Proxy Failed`, `In Flight`, `Avg Proxy Time`, `Proxy Prompt Tok`, `Proxy Gen Tok`, `Ban Rate`, `Backtracks` and `Upstream Scrapes`
- **New formatting units** — `format_duration()` (`820 ms` / `2.4 s` / `1m 12s`), `format_rate_per_minute()` (`18.0/min`) and `format_ratio()` (`75%`, and `-` for a zero denominator, because "nothing has fired yet" is not "0%"). Bans and back-tracks are rare enough that a per-second figure is always a small fraction, so the table shows them per minute
- **No prompt, request-payload, output-row or scoring-policy change** — this only reads more of an endpoint that already existed and rearranges a diagnostics tab. A config with `metrics.antislop_columns: false` and a plain vLLM is byte-identical to v13.3.0
- **New tests** — `tests/test_vllm_metrics.py` gains 11 checks (51 total): the full proxy metric set is summarised, the per-label series are kept, a failed request is one that is not 2xx, the per-label series are `None` for a plain vLLM, the ban/back-track/duration rates come from two snapshots and are `None` for one, a row carries every new key, each slot keeps its own throughput history (two slots on one server do not overwrite each other), the ring is bounded and resettable, and the three new formatters. `tests/test_metrics_tab_ui.py` gains 12 checks (28 total): the KPI cards exist and are populated, they read the polled figures, they do not double-count two slots on one proxy, the columns show themselves for a proxied slot and stay hidden for a plain vLLM, the table's two scrollbars are at least 16px wide, the graph stack's scrollbar is a real `tk.Scrollbar` at least 16px wide, the graph stack actually overflows and every panel is laid out inside it, all four graph panels exist, and the slot / proxy / queue panels each draw the right number of lines
- **Version bumped to v13.4.0** — a **minor** bump: a user-visible overhaul of the tab plus new figures, with no new required config key

### v13.3.0
- **New: the 📊 Metrics tab can show the antislop-vllm-fork proxy's own metrics (opt-in)** — the fork's `GET /metrics` now serves its own `antislop:` counters alongside the upstream vLLM body, so setting `metrics.antislop_columns: true` adds four columns to the tab: **Proxy Requests**, **Bans (fixed/total)**, **Proxy Errors** and **Proxy Gen Speed**. One URL, both sets of figures — the vLLM columns are untouched, because the fork passes the upstream body through verbatim
- **A fork whose upstream vLLM is down is now REACHABLE, not `unreachable`** — the fork still answers `/metrics` with its `antislop:` half and `antislop:upstream_metrics_scrape_total{result="error"}`, so `poll_endpoint()` accepts a body with **either** the `vllm:` or the `antislop:` prefix. Only a body with **neither** is still "not a vLLM endpoint". Before this, every slot pointed at the fork showed `unreachable` and no figures at all, even though the fork forwards to a vLLM that serves `/metrics` correctly — confirmed against a plain vLLM instance
- **`Bans (fixed/total)` is the ban-list tuning figure** — a large total with a small fixed count means the ban list is firing on things the model cannot avoid (a character's name, a word the user just used), and each of those costs a back-track and a restart for an answer that rarely improves. `summarise_antislop()` splits `antislop:ban_events_total` by its `fixed` label so the pair is available
- **`Proxy Gen Speed` is deliberately NOT the vLLM `Generation Speed` column** — vLLM's figure divides generation tokens by the server's own decode timer, so it measures the GPU; the proxy's divides by the **wall clock** between two polls, so it measures what the client received end to end. The gap between the two columns is the proxy's own overhead, which is the whole reason to show both. `compute_antislop_rates()` is a separate function from `compute_rates()` for exactly this reason, and reuses `_delta()` so a restarted proxy drops the sample instead of drawing a spike
- **Backwards compatible by construction** — a plain vLLM body has no `antislop:` metric, so `summarise_antislop()` returns `None` for every figure and the row carries no invented zeroes; `is_antislop_metrics()` is a separate test from `is_vllm_metrics()` rather than folded into it. A vLLM-only server's row is byte-identical to v13.2.1
- **The four columns are always CREATED and hidden with `displaycolumns`** (`generate.METRICS_ANTISLOP_COLUMNS`, `_apply_metrics_columns()`), so switching the key on needs no UI rebuild and the tree's column order never shifts. `_apply_metrics_columns()` runs on every refresh, so a config reload takes effect without restarting
- **`metrics.antislop_columns` ships `false`** — a plain vLLM serves no `antislop:` metrics, so the columns would be empty dashes for anyone not running the fork. A default run's tab is unchanged
- **New tests** — `tests/test_vllm_metrics.py` gains 12 checks (40 total): an antislop body is recognised, the proxy counters are summarised, a plain-vLLM body yields `None` antislop figures, a fork with a dead upstream is reachable rather than an error, a body with neither prefix is still an error, a fork row carries both sets of figures, the proxy speed comes from two snapshots, a single snapshot and a restarted proxy both report no speed, and the config key defaults off. `tests/test_metrics_tab_ui.py` gains 3 checks (16 total): the columns exist but are hidden by default, are shown when the key is on (without dropping the vLLM columns), and every row carries a value for every column — a short row would silently shift every cell after it
- **No prompt, request-payload, output-row or scoring-policy change** — this only reads a new endpoint and adds optional columns. A config with `metrics.antislop_columns: false` is byte-identical to v13.2.1
- **Version bumped to v13.3.0** — a **minor** bump: a new user-visible feature (the four columns) with no new required config key

### v13.2.1
- **Fixed: any run with no datasets configured failed every task with `UnboundLocalError: style_list_for_task`** — the v13.2.0 `{style}` deal read `style_list_for_task`, but that name was only bound inside `if dataset_binding is not None:`. With `datasets.sources: []` the binding block never runs, so the variable was unbound and **every task died on its first turn** before a single request was sent. It is now defaulted to the authored `style_list_local` before the binding, so a dataset-free run behaves exactly as it did before v13.2.0. This is why the v13.2.0 style feature could not be exercised end to end on a plain config
- **Fixed: the `{style}` instruction leaked into saved messages, and the guard that removes it** — the shipped prompts interpolate the style as `Begin this message as follows: {style}`, and some models echo that clause back as the **first line of the reply** instead of writing prose. Because the shipped styles are imperatives (`open on a sound…`), the echo reads as a stage direction pasted above the message. Measured on a 3-conversation run against a vLLM endpoint: **18 of 72 messages (25%)**, and clustered in ONE conversation — the model that had been given a style echoed it for all nine later turns of that row. The leak is **never an exact copy** of a pool entry (the model paraphrases: `someone entering the shop` for `someone entering or leaving`), so matching the configured strings cannot work. New `text_utils.strip_style_instruction_leak()` matches the imperative verb the style always opens with, drops the leading line only when it is a standalone clause and real prose follows it, and takes the blank lines that separated them with it. It is deliberately conservative: a message that is ONLY an instruction, an instruction that is not the first line, and ordinary prose that merely contains the word `open` (as dialogue, mid-sentence, or a real capitalised sentence) are all left untouched, because deleting a real opening sentence would be a worse failure than leaving one ugly line. Called from `worker()` on the accepted answer, **gated on `if task_style:`** so a style-free run is byte-identical. Verified 18/72 → 0/72 on a re-run
- **Fixed: a scene cast arrival could be scheduled on the FINAL reply** — `_build_scene_cast_plan()` placed a join at `total_slots - 1`, so with the shipped `num_turns: 12` the newcomer arrived on reply 12 and had **no reply left to be present in**. The leave used `max(2, total_slots*3//4)`, which left only two replies of aftermath. Both are re-anchored against the assistant slot count: the join at the **first third** and the leave at the **halfway point**, each clamped to leave real room. On a 12-reply conversation the arrival moved from reply 11 to **reply 4** and the exit from reply 9 to **reply 6**
- **Fixed: a 3-character scene with `min_present: 2` silently dropped to ONE character present** — a join and a leave each cost one present character, and both draw on the **same** pool of spare characters. With one spare the scene can afford the newcomer OR the departure, not both at once, so scheduling the leave before the arrival landed left the scene one character short of `min_present` for every reply in between (measured: slot 10 of a 12-reply plan). The exit is now deferred to the arrival reply, which hands the spare character over instead of spending it twice
- **Fixed: `tests/test_scene_cast.py`'s `min_present` check was VACUOUS, which is how the defect above shipped** — it read `_cast_names_for_slot()` for every slot but **never advanced the state between them**, so a scheduled exit never took effect, no post-exit slot was ever examined, and a plan that dropped the scene to one character passed. It also only covered 4/6/8/10 slots, never 12 (the shipped default). The check now advances the state per slot, the slot sweep includes 12-reply plans for 3/4/5 characters, and a new timing block asserts an arrival and an exit each leave at least one reply to be present in / to follow
- **New test: `tests/test_style_leak_guard.py`** (headless, 19 checks) — pins the leak guard: an instruction on its own line is removed with its blank lines, leading whitespace is preserved, every shipped style verb is handled, and the guard refuses to strip a message that is only an instruction, an instruction that is not first, a first line that runs on into prose, or empty input; plus AST checks that `worker()` calls the guard and does so **inside** an `if task_style:` gate
- **Fixed: `tests/test_progress_accounting.py` was FLAKY (measured 2 failures in 6 runs) and would have blocked a clean release gate** — its first case asserts the **async handoff**: the worker returns without marking the task complete or crediting it, and the processor thread does both afterwards. With an unguarded stub judge that handoff is a race, because the processor can score, write, mark complete and credit while the worker is still in its epilogue; both of that case's checks then read the **post-processor** state and fail intermittently while the product is behaving correctly. The judge is now held on an `Event` until the worker's epilogue has run, so the ordering the case is about is deterministic rather than probable. This is a TEST fix, not a product change — the product was never wrong. Verified 0 failures in 15 consecutive runs, and verified the case still catches the real regression by injecting the v13.0.5 no-credit bug (13 checks fail when it is present)

### v13.2.0
- **Fixed: about 18% of saved rows opened on the same three or four words** — measured on the operator's dataset, roughly one row in five shared its opening three or four words with another row. The cause is not a bad prompt, it is a **constant** prompt: every request carried the same instruction, so the model's most probable opening was the same one every time, and no detector could see it because the repeated-opener and repeated-reply guards both compare a reply with **its own conversation**, never with the run
- **New `{style}` variable, filled in EVERY authored prompt** — the question, answer, user continuation, greeting and first-line prompts each name `{style}`, and each fills it from **one value per conversation** (`generation.fill_style_variable()` / `fill_answer_prompt()` / `generate_question()` / `generate_user_continuation()` / `fill_greeting_prompt()` / `generate_first_line()`). It is dealt **once per task, never per turn**: a conversation whose style changed between turns would read as two scenes stitched together, and the style is part of what the row's first line was told to be. It is applied LAST in every formatter, so a style entry that happens to contain another token is inserted literally instead of being substituted again
- **The styles are dealt WITHOUT replacement across the run** — new `generation.deal_style()` mirrors `deal_random_names()`: the configured pool is shuffled into a deck and consumed in order, and a fresh pass is shuffled only when it runs out. That is the part that matters. Independent `random.choice` draws **redraw with replacement**, so over a few thousand rows a 12-entry pool leaves some entries dealt four times more often than others — and those are exactly the rows that still share an opening. Walking the deck gives every entry the same share: measured, 1,200 deals over a 12-entry pool touch all 12 entries **exactly 100 times each**. The deck is module-level RUN state under `app_state.style_deck_lock`, so every worker deals from the same pass, and it is cleared at run start in both the GUI and the headless paths

The entries describe **how a message BEGINS** (a sound, a gesture, mid-action, dialogue with no narration, an object being handled, a refusal, a sensory detail…) rather than a mood or a genre, because two rows can both be "tense" and still open on the same words while one opening on a sound and one mid-action cannot. The list is shipped in `config/config.yml` and mirrored as `generation.DEFAULT_STYLE_VARIANTS`, so an empty list falls back to the built-ins rather than silently disabling the feature. `enabled: false` restores the pre-v13.2.0 prompts exactly, with `{style}` resolving to nothing

### v13.1.1
- **Fixed: a long run slowed down and "paused, then started again" as it went** — the report was generation running fast for the first few hundred turns and then stalling in bursts, with the ETA jumping from about 3 hours to 12+. The cause was `generation.save_generation_state()`. It serialises the WHOLE run state, and `completed_task_ids`, `progress_credited_task_ids` and `quality_scores` all grow with the task count, so **one save costs more the longer the run goes**. It was called **synchronously on every completed task** from every worker and, under `quality.async_scoring`, from every judge thread too, and every one of those calls serialised on the single `app_state.state_file_lock`. A 40-thread run with a 12-wide async judge therefore queued every completion behind one growing JSON dump: **measured at 0.19 s per save at 500 tasks, 1.4 s at 4,000 and 4.3 s (8.4 s worst case) at 12,000**. That is quadratic in the task count, and it is exactly why the symptom appeared after a few hundred turns and got worse from there
- **The per-task path no longer writes the file itself** — new `request_generation_state_save()` marks the state dirty and returns immediately; one background `GenerationStateWriter` thread performs the write and **coalesces** every request that arrives while a dump is in flight or inside a 2 s debounce window. A burst of 40 simultaneous completions now costs **one** dump instead of 40. Measured: 208 concurrent requests from 52 threads finish in **5 ms**, with a per-call cost of **0.001 ms** (it was 4.3 s median / 8.4 s worst before), and 400 requests from 40 threads collapse into at most a handful of dumps
- **`save_generation_state()` itself is unchanged and still synchronous** — it stays the run-END and test path, where the file must be complete by the time the call returns. The new `flush_generation_state()` stops the writer and writes synchronously, and every run-end path uses it (`generate.py`'s Quit and main `finally`, the GUI's completion path, and `control.py`'s stop and shutdown), so **the final state on disk is always current and no writer thread outlives a run**. A crash can now lose at most the last 2 s of completions, which resume simply re-runs — the same trade the async quality queue already makes for rows
- **New headless regression test: `tests/test_state_save_coalescing.py`** — 10 checks: the per-task call returns in under 50 ms **even while the state lock is held** (so it provably never takes that lock), 400 requests from 40 threads coalesce into 1-5 dumps rather than one per request, `completed_task_ids` / `progress_credited_task_ids` / `quality_scores` all round-trip after a flush (resume data intact), the synchronous path is still synchronous and writes the current state, and an AST check that `worker()`'s own body never calls the blocking save while still requesting a coalesced one — with comments stripped, so a note that mentions the function is not mistaken for a call
- **Also: the per-request prompt traces are now opt-in (`generation.debug_prompt_log`, default `false`)** — `output/debug_prompt*.jsonl` was written **unconditionally**: one append per request of a multi-kilobyte line, from all 40 workers plus every judge thread, to a file with no size cap, and nothing reads it during a run. It is pure diagnostic overhead on the request path, so it now follows the project's rule that expensive features are opt-in. Measured at only ~0.004 ms per request, so **this was not the cause of the slowdown** — it is a separate, worthwhile cleanup. The entry is also no longer built at all when tracing is off, not merely skipped at the write. All six write sites (`generation.py` × 4, `quality.py` × 2) now go through the one gate in `logging_config` (`debug_prompt_logging_enabled()` / `write_debug_prompt()`), which is read at CALL time so a toggle takes effect without a restart; the GUI gets a **📝 Prompt Trace** checkbox and the Config Editor a matching field. Guarded by `tests/test_prompt_trace_gate.py`

### v13.1.0
- **New: a 📊 Metrics dashboard tab that reads vLLM's own `/metrics` endpoint** — the generator had no way to see whether its API servers were actually working well. A slot could be slow because the model was saturated, because a queue had built up, or because prefill was the bottleneck, and nothing in the UI distinguished those. vLLM already exposes exactly that on `/metrics` (Prometheus text, on the same port as its OpenAI API), so the new tab reads it and shows three figures **per API endpoint, never aggregated**: **Prompt Speed** (prompt tokens per second of prefill time), **Generation Speed** (generation tokens per second of decode time) and **Endpoint Load** (the server's `kv_cache_usage_perc` as a percentage), plus the running/waiting request counts that explain a high load. A graph under the table plots speed and load over time with **one line per endpoint**
- **Every endpoint is counted separately and is labelled in plain English** — one row per API slot that has a vLLM backend: **API 1**-**API 4**, **API 5 (Slop Fixer)**, **API 6 (Anti-Slop Fixer)** and **Judge (Quality)**. Nothing is summed into a single "total" row

The first poll after a start only records a baseline and shows `-`, and a **negative** delta (a restarted server) drops that sample instead of drawing a spike

- **Only vLLM backends appear** — a slot whose URL answers with no `vllm:` metric is reported as "not a vLLM endpoint" rather than being given invented figures, and a slot with no URL gets no row at all. An unreachable endpoint keeps its own row, marked `unreachable`, instead of vanishing

### v13.0.5
- **Fixed: with `quality.async_scoring: true`, the progress bar stalled around 60 turns and oscillated up and down while generation kept producing answers** — this was a **progress-accounting** defect, not a generation stall. The bar reads `app_state.task_queue.processed_tasks`, and three places mutated it inconsistently: the worker incremented it **per turn** the moment an answer arrived (speculative — before the task was validated, written, scored or accepted), the worker's epilogue **refunded** those turns whenever the task was not yet in `completed_task_ids` (the intent: a retry must not double-count), and the async path's completion (`_mark_task_written()`, which runs on a **processor thread** long after the worker returned) added the id to `completed_task_ids` but **never credited progress at all**. Under `async_scoring` the worker always reaches the refund **before** the row exists, so the four turns it had just counted were always given back and nothing ever re-added them: **a successfully completed async task contributed exactly zero**. The bar's value was therefore pinned to the number of turns *in flight* — bounded by `api.apis[0].threads` (40), not by the 12,000 turns queued — which is the observed ~60, and it wobbled rather than sitting still because a fast judge could land the id before the refund. Restarting did not help (the counter is persisted), and the resume path *also* re-credited already-completed tasks on top of the snapshot
- **Progress is now credited once per completed TASK, idempotently, and never refunded** — one new helper, `generation._credit_task_progress(task_id, turns=None, queue=None)`, adds one task's turns (capped at `total_tasks_for_progress`) and records the id in `app_state.progress_credited_task_ids`, so the sync write path, the async processor and a resumed run can all call it without double-counting. The speculative per-turn increment and the epilogue refund are **deleted**, and the two judge-drop branches credit too: a task the judge rejects is finished work, so without that 100% would be unreachable by construction (the drop stays visible in `dropped_task_ids`)
- **Fixed the same field's resume double-count** — `start_processing()` seeds `processed_tasks` from `processed_tasks_snapshot` and now also seeds the credited set from it, and the worker's "skip an already completed task" branch no longer increments `processed_tasks` at all. Before, the snapshot already counted those turns *and* the skip path added them again on every resume
- **The credited set is persisted** in `generation_state.json` as `progress_credited_task_ids`, falling back to `completed_task_ids` for state files written before this release (where every completed task was indeed already counted). It is run progress, not configuration, so it is deliberately **absent** from `config_snapshot` and from the resume-compatibility check
- **The ETA is unaffected** — the duration sample the deleted block also did (`q.start_times_list.append(...)`) is kept, so `estimate_time_remaining()` still has samples
- **New regression test: `tests/test_progress_accounting.py`** — eight headless cases: an async-scored task credits its turns once (the case that would have caught the bug), no refund when the judge is slower than the worker's epilogue, idempotence, a resume not double-counting, a judge-dropped task still crediting, a monotonic counter over a run of tasks, the credited set's state-file round trip, and (by `ast`) that both resume paths seed it while the increment and refund are gone
- **Duplication mode is deliberately untouched** — its per-API `api_processed_tasks` counter has the mirror-image bug (it over-counts because it is never refunded); do not "fix" it by copying the old refund logic, and do not extend the refund pattern to it
- **Version bumped to v13.0.5** — a **patch** bump: no prompt, output, request or scoring-policy change. A default run (`async_scoring` off) produces the same dataset; only the progress bar's arithmetic changes

### v13.0.1
- **Fixed: `shutdown` reported success but left the controller process running at ~90% CPU** — `ControlServer.start()` already puts a `serve_forever` loop on its own thread, and `ControlServer.serve_forever()` then started a **second** loop over the same `BaseServer`. Two loops share one `__shutdown_request` / `__is_shut_down` pair, so whichever exited first ran the `finally` block and reset the flag out from under the other; `stop()` then closed the socket, leaving the survivor calling `accept()` on a closed socket — `select()` reports it readable, `accept()` fails `EINVAL`, `_handle_request_noblock()` swallows the error, and the loop spins forever. It was a race, so it leaked on roughly two runs in three and looked like a flaky machine rather than a bug. Worse, it was **invisible to the CLI**: `shutdown` had already removed the socket, so `status` reported `no_daemon` and every later verb exited `3`. `serve_forever()` now parks the calling thread on a new `_stopped_done` event instead of starting a second loop, and `stop()` sets that event **last**, after the socket is unlinked, so teardown always completes before the thread returns. Verified with 10 consecutive `launch`/`shutdown` cycles (10/10 clean, versus 4/6 leaking before) and on the SIGTERM path used by systemd
- **New test: `test_serve_forever_returns_when_the_server_is_stopped`** — asserts **exactly one** accept loop is started per server, by counting calls to `_ThreadedUnixServer.serve_forever`, and that the serving thread has finished after `stop()`. The structural assertion is the important one: a timing-only assertion passed against the buggy code, because the race does not fire on every run. `tests/test_cli_control.py` is now 33 checks

Every verb the GUI has is reachable: `launch`, `serve`, `status`, `version`, `start`, `stop`, `pause`, `resume`, `stats`, `export`/`save`, `clear`, `wait`, `shutdown`, and `shell`. Built for a shell script and for an LLM agent as much as for a person, so the JSON is the contract and the human table sits on top of it. See [`docs/cli.md`](cli.md)
- **Three new GUI-free modules, and the boundary is enforced** — `run_config.py` resolves a config into a run and owns the output/DB/JSONL plumbing; `control.py` is the protocol, the socket server and `HeadlessController`; `cli.py` is the argparse surface, the client and the daemon launcher. `generate.py` builds the whole Tk UI at module scope, so **none of them may import it** — doing so would make every headless verb require a display. `tests/test_cli_control.py` scans the source with `ast` and fails on any import outside the one allowed GUI-launch path. The dependency chain stays one-way: `cli` → `control` → `run_config` → `generation`/`quality`/`app_state`
- **Machine-readable by default, and the exit code is the contract** — every verb prints one JSON object when stdout is not a terminal, so a script parses it with no flags; `--json` forces JSON on a terminal and `--text` forces the table when piped. `--json`, `--text`, `--config` and `--socket` work **before or after** the verb, because argparse only accepts them before the subcommand and an LLM cannot be relied on to remember that. Exit codes: `0` ok, `1` failed, `2` usage, `3` nothing to talk to, `4` already running, `5` refused, `6` timeout. Several codes deliberately share a status, so `error.code` in the JSON distinguishes them when it matters
- **`stats` reports both meanings of "filtering", kept apart** — **`detected`** is caught and handled (rewritten or retried) and the row is still written; **`filtered`** is dropped and never written, keyed by reason (`invalid_json`, `logic_zero`, `judge_failed`, `manual`); **`detection_config`** is which checks are actually armed. A counter reading zero means either "nothing was caught" or "the check is switched off", and only the third section tells them apart. Conflating the first two leads a reader to conclude the dataset is smaller, or cleaner, than it is. `--filters-only` returns just those three
- **The rate limiter is now interruptible, so Stop actually stops** — `RateLimiter.wait_if_needed()` slept with a plain `time.sleep()`, which cannot be interrupted. A rate-limited slot can wait almost a full minute before its next request is allowed, so a Stop had to wait out that minute before any worker noticed it — on a rate-limited slot the generator looked unstoppable for up to 60 s after the Stop was accepted. `_interruptible_sleep()` now sleeps in 0.25 s slices and returns as soon as `app_state.stop_processing` is set. The slot's request timestamp is still recorded, so nothing is over-sent: a stop only means the next request is not made. **Measured with `rate_limit_rpm: 2`:** `stop` returns `generation stopped` immediately instead of timing out
- **Fixed: `stop` reported a working stop as a timeout, three separate ways** — (a) `_join_workers(timeout)` applied the budget **per thread**, so ten workers with a 30 s timeout meant a real budget of 300 s, and the caller's own 30 s socket timeout fired first; (b) the client's socket timeout equalled the server's stop budget, so the client always gave up first; (c) a worker blocked inside a request cannot be interrupted, and a stop that ran out of time was reported as an **error** even though the run was genuinely stopping. `_join_workers()` now uses ONE shared deadline and **returns** the workers still alive rather than dropping them (dropping them would let a later run start on top of them); `cmd_stop()` reports `still_stopping` with a note instead of failing; the CLI's socket timeout is the stop budget plus 15 s
- **Fixed: `status` said `idle` while workers were still writing rows** — a reader told "idle" would reasonably treat the dataset as final and the process as safe to kill. That mismatch is exactly what a slow HTTP call produces: the queue drains, `processing_active` clears, and two workers stay alive for another 300 s. `phase()` now reports `stopping` while a worker is alive, `status` reports `running = processing_active or workers_alive()` plus a narrower `generating` flag, and the human table names the three states distinctly. Live workers also win over the remembered phase, so a stop whose workers then exited in the background no longer reports `stopping` forever
- **Fixed: `control.allow_remote` was documented in the config but never implemented** — the TCP listener would bind `0.0.0.0` happily, so a control channel that can TRUNCATE the database was reachable from the network the moment anyone set `tcp_host`. `ControlServer(allow_remote=...)` plus `_check_tcp_host()` now refuses any non-loopback bind unless it is set, and `_is_loopback_host()` accepts only `127.0.0.0/8`, `::1` and `localhost` (a hostname that resolves off-box counts as remote). Enabling TCP must not be the same thing as exposing the generator
- **Fixed: `save` doubled the row count on every save** — `jsonl_output_files()` swept in its own previous export, so each save re-read the last one. `DERIVED_OUTPUT_PREFIXES` is now one list used by BOTH `save` and `clear`, so the two cannot disagree about which files are derived output. Re-saving to the same destination is also no longer refused: the destination is dropped from the source list so it is never read while written
- **Fixed: four of ten detection counters reported `per_api: {}`** — the `app_state` attribute names are not consistent (`refusal_count_total` is singular, `ooc_count_total` is abbreviated, `logic_issue_count_total` sits next to `recent_logic_total`), so deriving a name from a stem silently produced an empty map. `DETECTION_COUNTERS` is now one explicit table of attribute names, used by both the stats payload and the stats reset, and a test asserts every row resolves to a real attribute
- **The GUI's DB actions now use the same implementation as the CLI** — `clear_database()`, `export_db_to_jsonl()` and `init_database_pool()` in `generate.py` are thin wrappers over `run_config`, keeping every `toast`/`messagebox` line so the window's behaviour and wording are unchanged. Two implementations of the same TRUNCATE is how the two front ends drift apart
- **The GUI can also serve the control interface, off by default** — `control.enabled: false` by default, so `python generate.py` behaves exactly as before. Set it to `true` (or tick **Serve control commands** in **Edit Config → Control Interface**) to drive a running window from a terminal. `start_control_server_if_enabled()` swallows every failure to a log line: a busy port must never stop the GUI opening, because being unable to drive the generator from a terminal is an inconvenience and refusing to start is a regression
- **New `control:` config block and Config Editor group** — `enabled`, `socket_path`, `tcp_host`, `tcp_port` and `allow_remote`, with a **Control Interface (CLI)** group in the editor that enables its entries only while the checkbox is on and validates the port as 1-65535 before saving
