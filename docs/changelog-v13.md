# 📝 Changelog — v13.x

Newest first. [v12](changelog-v12.md) holds the rest of the history.

### v13.0.5
- **Fixed: with `quality.async_scoring: true`, the progress bar stalled around 60 turns and oscillated up and down while generation kept producing answers** — this was a **progress-accounting** defect, not a generation stall. The bar reads `app_state.task_queue.processed_tasks`, and three places mutated it inconsistently: the worker incremented it **per turn** the moment an answer arrived (speculative — before the task was validated, written, scored or accepted), the worker's epilogue **refunded** those turns whenever the task was not yet in `completed_task_ids` (the intent: a retry must not double-count), and the async path's completion (`_mark_task_written()`, which runs on a **processor thread** long after the worker returned) added the id to `completed_task_ids` but **never credited progress at all**. Under `async_scoring` the worker always reaches the refund **before** the row exists, so the four turns it had just counted were always given back and nothing ever re-added them: **a successfully completed async task contributed exactly zero**. The bar's value was therefore pinned to the number of turns *in flight* — bounded by `api.apis[0].threads` (40), not by the 12,000 turns queued — which is the observed ~60, and it wobbled rather than sitting still because a fast judge could land the id before the refund. Restarting did not help (the counter is persisted), and the resume path *also* re-credited already-completed tasks on top of the snapshot
- **Progress is now credited once per completed TASK, idempotently, and never refunded** — one new helper, `generation._credit_task_progress(task_id, turns=None, queue=None)`, adds one task's turns (capped at `total_tasks_for_progress`) and records the id in `app_state.progress_credited_task_ids`, so the sync write path, the async processor and a resumed run can all call it without double-counting. The speculative per-turn increment and the epilogue refund are **deleted**, and the two judge-drop branches credit too: a task the judge rejects is finished work, so without that 100% would be unreachable by construction (the drop stays visible in `dropped_task_ids`)
- **Fixed the same field's resume double-count** — `start_processing()` seeds `processed_tasks` from `processed_tasks_snapshot` and now also seeds the credited set from it, and the worker's "skip an already completed task" branch no longer increments `processed_tasks` at all. Before, the snapshot already counted those turns *and* the skip path added them again on every resume
- **The credited set is persisted** in `generation_state.json` as `progress_credited_task_ids`, falling back to `completed_task_ids` for state files written before this release (where every completed task was indeed already counted). It is run progress, not configuration, so it is deliberately **absent** from `config_snapshot` and from the resume-compatibility check
- **The ETA is unaffected** — the duration sample the deleted block also did (`q.start_times_list.append(...)`) is kept, so `estimate_time_remaining()` still has samples
- **New regression test: `tests/test_progress_accounting.py`** — eight headless cases: an async-scored task credits its turns once (the case that would have caught the bug), no refund when the judge is slower than the worker's epilogue, idempotence, a resume not double-counting, a judge-dropped task still crediting, a monotonic counter over a run of tasks, the credited set's state-file round trip, and (by `ast`) that both resume paths seed it while the increment and refund are gone
- **Duplication mode is deliberately untouched** — its per-API `api_processed_tasks` counter has the mirror-image bug (it over-counts because it is never refunded); do not "fix" it by copying the old refund logic, and do not extend the refund pattern to it
- **Version bumped to v13.0.5** — a **patch** bump: no prompt, output, request or scoring-policy change. A default run (`async_scoring` off) produces the same dataset; only the progress bar's arithmetic changes

### v13.0.4
- **Fixed: the Slop Fixer, the Anti-Slop Fixer and the Quality Judge never sent `chat_template_kwargs`, so a reasoning model thought on every one of those requests no matter what the Samplers tab said** — only the four **main** generation request builders in `generation.py` read `samplers.enable_thinking`. The three auxiliary builders (`call_slop_fixer_llm`, `call_anti_slop_llm`, `_call_logic_judge_once`) emitted no `chat_template_kwargs` at all, so the server's default applied — thinking **ON** on a vLLM serving a reasoning model. The Samplers-tab **Thinking Mode: disable** therefore switched thinking off for question/answer/continuation/opening-mode requests and left it **on** for every rewrite and every score, which is where the time went: those are short, structured jobs, and on a local vLLM the chain of thought dominated their wall-clock time. Setting the default template to `false` on the server instead produced a **~5x generation speedup** in the reporter's runs, because it was the only thing that reached the judge and the fixers. All three now apply the setting
- **New: each auxiliary request has its own Thinking Mode, and `inherit` is the default** — `samplers.slop_fixer_enable_thinking`, `samplers.anti_slop_fixer_enable_thinking` and `quality.scoring_api.enable_thinking`, each accepting `inherit` / `default` / `enable` / `disable`. `inherit` follows the main `samplers.enable_thinking`, so a user who already set the Samplers tab to `disable` now gets thinking switched off for the fixers and the judge **with no new configuration**, which is the point. A request whose mode resolves to `default` sends no `chat_template_kwargs`, so a config that does not mention the new keys is **byte-identical to v13.0.3**
- **The new keys are SIBLINGS of the sampler dicts, not entries inside them, and that is load-bearing** — `slop_fixer_params` / `anti_slop_params` are read with an all-or-nothing `params or main_sampler_settings` fallback, and `quality.scoring_api.sampler_settings` is handed to the judge's payload builder as the sampler override. Putting a single `enable_thinking` entry inside one of those dicts makes it **truthy**, so it stops inheriting the main sampler defaults and the Slop Fixer's `top_p` silently jumps from the main `0.9` to its hardcoded `0.95` (`repetition_penalty` `1.0` -> `1.1`) on every rewrite — and a non-sampling key inside `sampler_settings` would also reach the wire as an unknown field. This was caught in review and is now pinned by `tests/test_thinking_mode.py::test_fixer_fallback_is_not_broken`, which runs the fixer with an empty params dict and asserts the main values survive
- **New: three dropdowns in the config editor** — **Thinking Mode (Slop Fixer)** and **Thinking Mode (Anti-Slop)** sit at the bottom of their existing sampler-override groups in the **Samplers** tab, and **Judge Thinking Mode** sits under the Quality Scoring API fields in the **Generation** tab. The main **Thinking Mode** help text now says the fixers and the judge follow it unless overridden, so the scope of that control is no longer ambiguous
- **One definition of the rule** — `api_handler.resolve_thinking_mode()`, `thinking_payload_fragment()` and `apply_thinking_mode()` are shared by `generation.py` and `quality.py`, so the two modules cannot drift on what `inherit` or a legacy boolean means. `api_handler` was chosen because `quality.py` already imports it and it must not import `generation.py`
- **Fixed the same omission in Regex Watch rewrites** — `rewrite_regex_watch_text()` runs on the main API but also sent no `chat_template_kwargs`; it now follows the main setting like the fixers do
- **New regression test: `tests/test_thinking_mode.py`** — pins the resolution rules (including the legacy boolean and an unknown value), the payload each of the three auxiliary builders actually sends, the Regex Watch path, and that the **shipped** config resolves to `default` everywhere so a default run stays byte-identical. Verified to fail on the old code: reverting the judge line fails five of its checks
- **Version bumped to v13.0.4** — a **patch** bump: no prompt, output or scoring-policy change. `inherit` plus the shipped `enable_thinking: default` resolves to "send nothing", exactly as before

### v13.0.3
- **Fixed: the async-scoring write path skipped `app_state.output_data_lock`, so a processor thread could interleave a row with a worker's** — `write_conversation()` appends with a bare `open(..., 'a')`/`write()` and takes **no lock of its own**; every caller is responsible for holding the lock. Every worker call site does, and `_make_duplication_turn_write_jobs()` did, but `_make_quality_write_job()` — the **non-duplication** async path — called `write_conversation()` bare. With `quality.async_scoring: true` the queue processors are real writers running concurrently with the workers, so two appends to the same output JSONL could interleave and split a line. The append now runs under `app_state.output_data_lock`, the same lock the workers and the Review tab's drop rewrite take
- **Corrected: the async mode's documentation said "the judge writes the rows", which is never what the code did** — the judge is an HTTP scorer; it returns a verdict and has no access to the output files. The write is done by the **queue processor thread** (`_score_and_write_job()`) through the writer that `generation.py` injects, and the only thing that ever appends is still `generation.write_conversation()`. The old phrasing was not just imprecise, it **hid the missing lock**: a judge needs no lock, a writer does, so "the judge writes" made an unlocked append read as correct. Reworded in `quality.py` (module comment, `_enqueue_quality_write()`, `_score_and_write_job()`, the queue-start log line), `generation.py` (`_make_quality_write_job()`, `_score_and_store_quality()`), `generate.py` (the async-start log line), `config_editor.py` (the checkbox label), `config/config.yml`, `docs/detection-and-quality.md`, `docs/agents/quality-queue.md`, `docs/agents/task-index.md` and the v12.9/v12.9.2 entries of `docs/changelog-v12.md`
- **No behaviour change for a default run** — `async_scoring` is off by default, and the lock is only taken on the async path, so a default run is byte-identical to v13.0.2

### v13.0.2
- **Fixed: the GUI's `Start processing:` line announced a thread count that was not the number of threads it started** — the line reported `app_state.num_threads`, the **legacy `api.threads` scalar**, while the launch loop below it summed the per-API `threads` of the active slots. The two are unrelated numbers: `api.threads` is only a fallback for when the per-slot counts are absent. A user with **Main API 1 set to 30 threads** saw `Start processing: 12 threads. Output: sharegpt...` and 30 threads actually start — and the GUI's own Threads card, which counts `app_state.threads`, correctly said 30. The log line was simply reporting a different variable
- **One definition of the worker total** — `run_config.count_worker_threads(api_configs, active_api_configs, master_duplication_enabled)` is now the only place the total is computed, and `total_threads_for_run(settings)` is a thin wrapper over it. `start_processing()` resolves the total through it **once, before** the `Start processing:` line, and the launch loop counts to that same variable, so the number logged and the number spawned cannot disagree. `app_state.num_threads` is then set to the resolved total, so the control server's `status`/`stats` payloads report the run's real worker count instead of the scalar (`control.reported_thread_count()` prefers the spawned count while a run is live and otherwise resolves what the next run would start)
- **New regression test, verified to fail on the old code** — `tests/test_worker_launch.py::test_reported_thread_count_is_the_launched_thread_count` parses `start_processing()` with `ast` and requires that the `Start processing:` line names `total_threads`, does **not** name `num_threads`, and is logged **after** the total is resolved through `run_config.count_worker_threads()`; it also requires the launch loop to be `for i in range(total_threads)`. Reverting the log line to the scalar fails it with `'total_threads' not found in {'app_state', 'num_threads', ...}`. Checked end to end against the reported config (slot 1 at 30 threads, legacy scalar 10): the total resolves to **30**, not 12
- **Version bumped to v13.0.2** — a **patch** bump: no new settings, no prompt/request/output change. A default run is byte-identical to v13.0.1; only the log line and the reported status count change

### v13.0.1
- **Fixed: `shutdown` reported success but left the controller process running at ~90% CPU** — `ControlServer.start()` already puts a `serve_forever` loop on its own thread, and `ControlServer.serve_forever()` then started a **second** loop over the same `BaseServer`. Two loops share one `__shutdown_request` / `__is_shut_down` pair, so whichever exited first ran the `finally` block and reset the flag out from under the other; `stop()` then closed the socket, leaving the survivor calling `accept()` on a closed socket — `select()` reports it readable, `accept()` fails `EINVAL`, `_handle_request_noblock()` swallows the error, and the loop spins forever. It was a race, so it leaked on roughly two runs in three and looked like a flaky machine rather than a bug. Worse, it was **invisible to the CLI**: `shutdown` had already removed the socket, so `status` reported `no_daemon` and every later verb exited `3`. `serve_forever()` now parks the calling thread on a new `_stopped_done` event instead of starting a second loop, and `stop()` sets that event **last**, after the socket is unlinked, so teardown always completes before the thread returns. Verified with 10 consecutive `launch`/`shutdown` cycles (10/10 clean, versus 4/6 leaking before) and on the SIGTERM path used by systemd
- **New test: `test_serve_forever_returns_when_the_server_is_stopped`** — asserts **exactly one** accept loop is started per server, by counting calls to `_ThreadedUnixServer.serve_forever`, and that the serving thread has finished after `stop()`. The structural assertion is the important one: a timing-only assertion passed against the buggy code, because the race does not fire on every run. `tests/test_cli_control.py` is now 33 checks

### v13.0
- **New: headless / CLI control — the generator runs without a window** — `python -m cli` drives the same engine, the same `config/config.yml` and the same output files as the GUI, from a terminal. Every verb the GUI has is reachable: `launch`, `serve`, `status`, `version`, `start`, `stop`, `pause`, `resume`, `stats`, `export`/`save`, `clear`, `wait`, `shutdown`, and `shell`. Built for a shell script and for an LLM agent as much as for a person, so the JSON is the contract and the human table sits on top of it. See [`docs/cli.md`](cli.md)
- **Three new GUI-free modules, and the boundary is enforced** — `run_config.py` resolves a config into a run and owns the output/DB/JSONL plumbing; `control.py` is the protocol, the socket server and `HeadlessController`; `cli.py` is the argparse surface, the client and the daemon launcher. `generate.py` builds the whole Tk UI at module scope, so **none of them may import it** — doing so would make every headless verb require a display. `tests/test_cli_control.py` scans the source with `ast` and fails on any import outside the one allowed GUI-launch path. The dependency chain stays one-way: `cli` → `control` → `run_config` → `generation`/`quality`/`app_state`
- **Machine-readable by default, and the exit code is the contract** — every verb prints one JSON object when stdout is not a terminal, so a script parses it with no flags; `--json` forces JSON on a terminal and `--text` forces the table when piped. `--json`, `--text`, `--config` and `--socket` work **before or after** the verb, because argparse only accepts them before the subcommand and an LLM cannot be relied on to remember that. Exit codes: `0` ok, `1` failed, `2` usage, `3` nothing to talk to, `4` already running, `5` refused, `6` timeout. Several codes deliberately share a status, so `error.code` in the JSON distinguishes them when it matters
- **`stats` reports both meanings of "filtering", kept apart** — **`detected`** is caught and handled (rewritten or retried) and the row is still written; **`filtered`** is dropped and never written, keyed by reason (`invalid_json`, `logic_zero`, `judge_failed`, `manual`); **`detection_config`** is which checks are actually armed. A counter reading zero means either "nothing was caught" or "the check is switched off", and only the third section tells them apart. Conflating the first two leads a reader to conclude the dataset is smaller, or cleaner, than it is. `--filters-only` returns just those three
- **The rate limiter is now interruptible, so Stop actually stops** — `RateLimiter.wait_if_needed()` slept with a plain `time.sleep()`, which cannot be interrupted. A rate-limited slot can wait almost a full minute before its next request is allowed, so a Stop had to wait out that minute before any worker noticed it — on a rate-limited slot the generator looked unstoppable for up to 60 s after the Stop was accepted. `_interruptible_sleep()` now sleeps in 0.25 s slices and returns as soon as `app_state.stop_processing` is set. The slot's request timestamp is still recorded, so nothing is over-sent: a stop only means the next request is not made. **Measured with `rate_limit_rpm: 2`:** `stop` returns `generation stopped` immediately instead of timing out
- **Fixed: `stop` reported a working stop as a timeout, three separate ways** — (a) `_join_workers(timeout)` applied the budget **per thread**, so ten workers with a 30 s timeout meant a real budget of 300 s, and the caller's own 30 s socket timeout fired first; (b) the client's socket timeout equalled the server's stop budget, so the client always gave up first; (c) a worker blocked inside a request cannot be interrupted, and a stop that ran out of time was reported as an **error** even though the run was genuinely stopping. `_join_workers()` now uses ONE shared deadline and **returns** the workers still alive rather than dropping them (dropping them would let a later run start on top of them); `cmd_stop()` reports `still_stopping` with a note instead of failing; the CLI's socket timeout is the stop budget plus 15 s
- **Fixed: `status` said `idle` while workers were still writing rows** — a reader told "idle" would reasonably treat the dataset as final and the process as safe to kill. That mismatch is exactly what a slow HTTP call produces: the queue drains, `processing_active` clears, and two workers stay alive for another 300 s. `phase()` now reports `stopping` while a worker is alive, `status` reports `running = processing_active or workers_alive()` plus a narrower `generating` flag, and the human table names the three states distinctly. Live workers also win over the remembered phase, so a stop whose workers then exited in the background no longer reports `stopping` forever
- **Fixed: `control.allow_remote` was documented in the config but never implemented** — the TCP listener would bind `0.0.0.0` happily, so a control channel that can TRUNCATE the database was reachable from the network the moment anyone set `tcp_host`. `ControlServer(allow_remote=...)` plus `_check_tcp_host()` now refuses any non-loopback bind unless it is set, and `_is_loopback_host()` accepts only `127.0.0.0/8`, `::1` and `localhost` (a hostname that resolves off-box counts as remote). Enabling TCP must not be the same thing as exposing the generator
- **Fixed: `save` doubled the row count on every save** — `jsonl_output_files()` swept in its own previous export, so each save re-read the last one. `DERIVED_OUTPUT_PREFIXES` is now one list used by BOTH `save` and `clear`, so the two cannot disagree about which files are derived output. Re-saving to the same destination is also no longer refused: the destination is dropped from the source list so it is never read while written
- **Fixed: four of ten detection counters reported `per_api: {}`** — the `app_state` attribute names are not consistent (`refusal_count_total` is singular, `ooc_count_total` is abbreviated, `logic_issue_count_total` sits next to `recent_logic_total`), so deriving a name from a stem silently produced an empty map. `DETECTION_COUNTERS` is now one explicit table of attribute names, used by both the stats payload and the stats reset, and a test asserts every row resolves to a real attribute
- **The GUI's DB actions now use the same implementation as the CLI** — `clear_database()`, `export_db_to_jsonl()` and `init_database_pool()` in `generate.py` are thin wrappers over `run_config`, keeping every `toast`/`messagebox` line so the window's behaviour and wording are unchanged. Two implementations of the same TRUNCATE is how the two front ends drift apart
- **The GUI can also serve the control interface, off by default** — `control.enabled: false` by default, so `python generate.py` behaves exactly as before. Set it to `true` (or tick **Serve control commands** in **Edit Config → Control Interface**) to drive a running window from a terminal. `start_control_server_if_enabled()` swallows every failure to a log line: a busy port must never stop the GUI opening, because being unable to drive the generator from a terminal is an inconvenience and refusing to start is a regression
- **New `control:` config block and Config Editor group** — `enabled`, `socket_path`, `tcp_host`, `tcp_port` and `allow_remote`, with a **Control Interface (CLI)** group in the editor that enables its entries only while the checkbox is on and validates the port as 1-65535 before saving
- **Docs: `README.md` "At a Glance" now shows both front ends, and `docs/architecture.md` was
  brought up to date** — the README diagram showed the Tk GUI as the only entry point, which stopped
  being true the moment a terminal could drive a run, so it now shows both front ends, the `control.py`
  socket protocol and `run_config.py` between them. `docs/architecture.md` had never been updated: its
  diagram and its module table both lacked the three new modules, so `run_config.py`, `control.py` and
  `cli.py` were added there with their real import edges (and `generate.py`'s row left as the root)
- **Docs: one new user page, one new agent topic file, and four index rows** — `docs/cli.md` is the
  user page (verbs, JSON, exit codes, the `control:` block, the files the CLI writes, a typical session and
  a troubleshooting table); `docs/agents/cli.md` is the LLM topic file (the dependency rule, a per-module
  edit guide, the tests, and the traps). Rows were added to `README.md`'s doc map,
  `docs/file-structure.md` (both the module list and the `docs/agents/` index),
  `docs/agents/task-index.md` and the `AGENTS.md` hub table
- **Removed: the "Slop and Anti-Slop are DISABLED BY DEFAULT" block from `README.md`** —
  **`README.md` only**; `docs/slop-and-antislop.md` and the topic docs still carry the full argument,
  so nothing was lost, and the README keeps its `Slop & Anti-Slop — Use the Fork` row in the doc map
- **No unintended edits, and that is asserted rather than assumed** — the tree was diffed against
  upstream and three pieces of collateral damage were found and undone: `tools/add_license_header.py` had
  put a 10-line SPDX header on `.gitignore` (a gitignore is not a source file), and two LF files
  (`docs/file-structure.md`, `docs/architecture.md`) had been rewritten with CRLF, which turns a
  handful of changed lines into a whole-file diff. This repository is genuinely mixed (20 CRLF files,
  98 LF), so the rule is **preserve whichever a file already uses** — `api_handler.py` is CRLF and was
  patched at the byte level for that reason
- **New tests** — `tests/test_cli_control.py` (32 headless checks: config resolution, worker-arg binding against the real signature, socket round-trip, every verb, the stats contract, exit codes, `_kind`-must-not-leak, save idempotency, stop semantics, TCP safety, default-GUI-unchanged). The three new modules were added to `tests/test_undefined_globals.py`'s `CHECKED_MODULES`
- **Version bumped to v13.0** — a **minor** bump: new feature, new config block, new modules. **A default GUI run is unchanged**: no socket is opened unless the daemon runs or `control.enabled` is on, and no worker option, prompt, request or output row changed
