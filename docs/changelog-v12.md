# 📝 Changelog — v12.x

Newest first. [v11 and earlier](changelog-v11.md) holds the rest of the history.

### v12.7 (Current)
- **Fixed: the duplicated assistant turn** — a conversation could come out with the same assistant reply repeated verbatim: three byte-identical 884-character turns in the reported run. The culprit was the **answer prompt**, not Valkey, not random names and not the response cache, and two independent defects combined. (1) `{subject}` is the **source-book chunk** — up to `generation.subject_size` characters of finished prose — and a prompt that wrote `You are writing the reply of the woman, {subject}, in an intense roleplay` was handing the model a ~1000-character slab in a slot whose grammar asks for a name. The most probable continuation of that instruction is to **reproduce the slab**, and every turn injected the *same* chunk, so every turn reproduced the *same* text. (2) Her reply was sent to the continuation request **twice** — once as the last message of the history the worker already appends it to, and once via `{last_assistant_message}` — so 43–65% of the man's continuation sentence was words she had just used, which fed the next answer request and closed the loop
- **New: `{character_name}`, `{character_names}` and `{character_profile}`** — the answer prompt's native variable set is now `{subject}`, `{context}`, `{character_name}`, `{character_names}`, `{character_profile}`. `{character_name}` is the first scene character's name, `{character_names}` every name joined by `, `, and `{character_profile}` the whole `CHARACTER N PROFILE` block, all filled from the same per-task values the profile block is built from, so the name a prompt writes is the name the profile's `Name:` line carries. `the woman, {character_name},` renders as `the woman, Marlowe,` — a name in a name slot, which is what the sentence's grammar asks for. They are also filled in `generate_question()` and `generate_user_continuation()`, where the same name-vs-chunk confusion existed
- **`{subject}`/`{context}` keep their documented meaning and are made safe to use** — they stay the **source passage** (removing them would break every prompt that relies on them, and the docs describe them as the passage) but the fill no longer produces malformed sentences. A chunk is whitespace-normalised before insertion, so a multi-paragraph slice cannot break the instruction's structure, and a trailing sentence terminator is stripped, so `... into her guts.` followed by the prompt's own comma no longer renders as `guts.,`. The `N/A` fallback for an empty chunk is unchanged. This is a pure formatting change inside `fill_answer_prompt()`: a prompt that names neither variable still comes back **byte-identical**, so a default run is unchanged
- **Fixed: her reply is sent once to the continuation** — `generate_user_continuation()` sent `[system] + conversation_history_for_llm + [user]`, and that history **already ends with her reply**, which the final user message then embedded again via `{last_assistant_message}`. When the template names the variable the trailing assistant message is now dropped from the history sent with the request, so the reply appears exactly once, in the slot the prompt names. The variable's value is unchanged, so the prompt still reads naturally, and a template that does **not** name it keeps the full history — the shipped `prompts.user_continuation_prompt` names no variables, so a default run sends byte-identical requests
- **New opt-in `generation.repeat_reply_guard`** — the sibling of the repeated-opener guard, for a reply repeated **whole**. `detection.is_repeated_opener()` compares the first few *content* words and catches a reused sentence frame (`She lets out a breath` / `She lets out a laugh`); a verbatim 884-character repeat shares no frame with anything because it **is** the earlier reply, so the opener check cannot see it. New `detection.is_repeated_reply()` compares the **whole** reply — whitespace-collapsed, case-folded, then a similarity ratio — and reports a hit at or above `REPEATED_REPLY_SIMILARITY` (0.92, so a repeat with a slightly rewritten tail is still caught). Replies under `REPEATED_REPLY_MIN_CHARS` (120) never hit, because two short replies can coincide innocently (`She nods.`) and staying quiet only suppresses a retry. On a hit the answer goes back to the **SAME main API slot** with one fix from `generation.repeat_reply_fixes` (or `DEFAULT_REPEAT_REPLY_FIX`) appended to the **answer prompt** — never the system prompt, the same cache contract the opener guard follows — bounded by `generation.repeat_reply_max_retries` (default 1). Once the retries run out the best-effort answer is **KEPT**, never dropped: a repeated reply is a style miss, not a reason to lose the row. A first assistant turn can never fire
- **The default fix points at the cause, not only the symptom** — it tells the model this is a **new turn** and that its earlier reply is already written, so the guard is useful even against a prompt the operator has not fixed yet. It runs **immediately after** the repeated-opener branch and **before** the success return, so it judges the text that is about to be written
- **All three keys default to off/empty/1**, so a default run is unchanged: the guard does not run, and no request differs from v12.6
- **Regression guards** — `tests/test_repeat_opener_and_answer_vars.py` gained headless cases for the character variables (`{character_name}` is a name and not the passage, `{character_names}` joins every name, `{character_profile}` carries the block, empty values fall back to `N/A`, a variable-free prompt stays byte-identical, a dataset alias still renders), for `_clean_chunk_for_inline()` (no `guts.,` for any trailing terminator, newlines and runs of spaces collapsed, idempotent), for the continuation trim (the reply appears exactly **once** when the template names it and the full history is kept when it does not), for `is_repeated_reply()` (the operator's verbatim pair, whitespace/case variants, a near-repeat, and a genuinely different reply left alone), and for the retry pipeline (same slot, system prompt and history byte-identical, fix on the answer prompt, best-effort reply kept on exhaustion). `tests/test_repeat_reply_ui.py` drives the REAL `ConfigEditor` and pins the save/load round trip for the three new settings, that the fix list survives verbatim (quotes, apostrophes and `->`), that the shipped defaults are off/empty/1, and that the two guards are **independent**
- **The shipped roleplay prompts were corrected** — all five carried defects that were invisible until the v12.7 work made the prompt text matter. (1) **`question` and `user_continuation_prompt` wrote `the users first/next message`**, missing the apostrophe, and then assumed **one female character** (`her words`, `her gender`, `her backstory`, `do not write her words`) although `prompts.character.num_characters` supports 1–10 and a profile's `Gender` field is authoritative — a run with a male character or a two-character ensemble was described to the model as something it was not. Both now say "the user's" and "every character"/"them", and `user_continuation_prompt` says "any character's" where it meant all of them, not just one. (2) **`answer` stated `CHARACTER INFORMATION:` unconditionally**, but the character engine can be off, so the block may never arrive; it is now "if a CHARACTER PROFILE block is present", matching the conditional wording every other block in the same prompt already used. (3) **`greeting` said `Speak to the user as you.`**, which is garbled — it means *address the user as "you"*, and is now written that way. It also said `do not describe them arriving` (plural pronoun for one user), and its "already there" clause now says the user is already **present** and repeats the noun instead of switching to `them`. (4) **`first_line` said `The message you receive is the scene so far`**, but that request sends the greeting as a single message, not a transcript, so it now says the message is the character's opening message. (5) `answer` gained one clause — "Answer what the user just said or did, and move the scene forward rather than restating what is already on the page" — which is the behavioural half of the duplicated-turn defect fixed above: the instruction that a new turn is a new turn. `DEFAULT_GREETING_PROMPT` and `DEFAULT_FIRST_LINE_PROMPT` in `generation.py` were updated in lockstep, because they are the fallbacks used when a config key is empty and `tests/test_opening_mode.py` asserts they match the shipped config
- **What did NOT change:** no template variable was added, removed or re-bound (`{recent_questions}`, `{context}`, `{speaker}`, `{chunk}`, `{style}` all still resolve), no block name was altered, and every prompt still names only blocks it actually receives. The `if a ... block is present` convention is preserved, so one shipped prompt stays valid for every feature combination. All six prompts survive `config_editor.sanitize_input()` verbatim, so an editor save does not corrupt them
- **Version bumped to v12.7** — the GUI version label in `generate.py`, the title of this README and this changelog

### v12.6
- **The project now targets Python 3.11, not 3.9** — the 3.9 floor was a self-imposed constraint, not a dependency requirement: nothing in `requirements.txt` needs an interpreter that old, and holding the floor at 3.9 meant every module had to avoid `match`, PEP 604 `X | Y` unions and PEP 585 builtin generics. The target is now 3.11, which is what the code is actually run and tested on. This is a **language-level retarget only**: no prompt text, no config key and no runtime behaviour changed, so a default run stays byte-identical to v12.5.1
- **The dataset modules were modernized to match** — `dataset_sources.py`, `dataset_templates.py`, `dataset_bindings.py` and `dataset_settings.py` were the only modules carrying `typing` imports, and they were rewritten to the 3.11 spelling: `Optional[X]` became `X | None`, `Tuple[str, ...]`/`Dict[str, Any]`/`List[...]` became `tuple[str, ...]`/`dict[str, Any]`/`list[...]`, and `typing.Mapping`/`Iterable`/`Iterator` became their `collections.abc` equivalents. The four `# type:` comments in `dataset_bindings.py` were updated in place and deliberately **not** converted to real annotations, because those attributes are assigned `None` before their real value and a real annotation would change what the class body evaluates. Every `isinstance(x, Mapping)` call site keeps working: `collections.abc.Mapping` supports `isinstance`, which is exactly why it replaced the `typing` alias rather than a bare `dict`
- **`generate.py` now refuses to start on an older interpreter** — the dataset modules use PEP 604 `X | None`, which is 3.10+ syntax, so on 3.9 the app used to die with a `SyntaxError` inside an import, several frames deep, with no hint about the cause. A guard immediately after the stdlib imports compares `sys.version_info` against `(3, 11)`, writes the required and the detected version to stderr, and exits 1. It runs **before** `text_utils`, `config_loader` and the `dataset_*` imports on purpose — a guard placed after them would never be reached. On 3.11+ it produces no output and no side effects
- **Regression guard** — `tests/test_python311_target.py` is headless and pins four things: the running interpreter is 3.11+; the four dataset modules import cleanly and their source text contains no `Optional[`/`Tuple[`/`Dict[`/`List[`/`typing.`; `isinstance` on the `collections.abc` imports still behaves, and `normalize_config({})`/`cell_to_text()`/`SourceBinding`/`TaskBinding` still accept a plain dict; and the `generate.py` guard both compares against `(3, 11)` and sits at a smaller character offset than the first 3.11-only import. That last check is the one that matters — it was verified to fail when the guard is moved below the imports, so it is not vacuous. `generate.py` is never imported by the test (that would build the Tk UI and need a display); its source is read from disk instead
- **Docs retargeted** — `AGENTS.md` now states the 3.11 target and **inverts** its old warning: `match` and `X | Y` unions are allowed and preferred over `typing.Optional`/`Union`, and the thing to avoid is now 3.12+ syntax such as PEP 695 `type` aliases and `class Foo[T]`. The same inversion was applied to both `style_metrics.py` rows in `docs/agents/core-modules.md`, and `README.md`, `docs/installation.md`, `docs/architecture.md`, `docs/agents/config.md`, `docs/dataset-bindings.md` and `requirements-datasets.txt` were updated to match. `docs/installation.md` also gained a line telling the reader an older interpreter is rejected at startup. Historical mentions of 3.9 in this changelog and of the Python 3.12 verification environment in `docs/dataset-bindings.md` were left alone — they record what past releases said and which interpreter a past run used, not the current target
- **Version bumped to v12.6** — the GUI version label in `generate.py`, the title of this README and this changelog

### v12.5
- **Fixed: the answer prompt's `{subject}` reached the model as literal text** — the question, continuation, greeting and first-line prompts all fill their native template variables at their own formatting boundary; the answer prompt had no such boundary, so a prompt that wrote `{subject}` sent the model the five characters `{subject}` instead of the passage. This is a silent defect with a visible symptom: a prompt that names the character through `{subject}` never actually names her, so the model refers to her only by pronoun or job title ("The archivist", "The captain"). New `generation.fill_answer_prompt()` is that boundary and fills `{subject}` and `{context}` from the task's own chunks, with an empty chunk becoming `N/A` rather than a dangling clause, exactly as the question path already does. It routes through `render_with_native_placeholders()` when dataset sources are attached, so an authored `{{ds:alias}}` keeps its single-pass guarantee. **The shipped answer prompt contains no variables, so a default run is byte-identical**; only a prompt that opts in changes
- **Fixed: nothing compared an assistant reply to the other replies in its own conversation** — `generation.history_size` prunes `app_state.question_history`, which is a list of recent opening *questions* fed to the question prompt. It never touched the assistant turns, and every retry check compares a reply against a phrase list or a rule, so a model that opened every reply the same way was invisible to all of them. The full history went to every answer call, so each reply saw the previous reply's opener and copied it: the tic compounded down the conversation (28.6% of first replies, 69.9% of fourth replies in the run that surfaced this). New opt-in **`generation.repeat_opener_guard`** compares a reply's opening content words against this conversation's earlier assistant replies via `detection.is_repeated_opener()`, and on a hit sends the answer back to the SAME main API slot for a fresh opener. A first assistant turn can never fire (there is nothing to repeat yet)
- **The repeated-opener rule matches a FRAME, not a phrase** — the reported tic was a fixed frame with a swapped object (`She lets out a breath`, `She lets out a laugh`, `She lets out a sigh`), which share only two words. A strict three-word match would miss every one of them while catching almost nothing else, and a set overlap would fire on two replies that merely reuse a common word later in the opener. The comparison is therefore a prefix of the opening content words that hits on two shared words when the openers then diverge, with stopwords and one-letter words dropped so `She` and `Her` cannot manufacture a match
- **The retry instruction rides on the ANSWER PROMPT, never the system prompt** — the answer prompt is the final user message, so changing it leaves the system prompt and the whole history byte-identical and a prefix-caching server still serves them. Appending to the system prompt would invalidate the cache for that slot on every retry, which is exactly the cost the `depth0` placements exist to avoid. Bounded by `generation.repeat_opener_max_retries` (default 1); once the retries run out the best-effort answer is KEPT, never dropped — a repeated opener is a style miss, not a reason to lose the row. `generation.repeat_opener_fixes` supplies the instructions (cycled, empty = a built-in default), and the guard records no dashboard timestamp because it is an opt-in retry trigger rather than an issue type
- **Regression guards** — `tests/test_repeat_opener_and_answer_vars.py` is headless and pins both defects: `{subject}`/`{context}` are filled, no literal token survives to the wire, a variable-free prompt is returned byte-identical, the detector separates a swapped-object frame from a genuinely different opener, and the retry leaves the system prompt and history untouched while keeping a still-repeating reply. `tests/test_repeat_opener_ui.py` drives the REAL `ConfigEditor` and pins the save/load round trip for the three new settings, including that the fix list is stored verbatim (quotes, apostrophes and `->` survive `sanitize_input()`)
- **Version bumped to v12.5** — the GUI version label in `generate.py`, the title of this README and this changelog

### v12.4
- **The answer prompt can now use the blocks the generator injects** — the shipped `prompts.question`, `prompts.answer` and `prompts.user_continuation_prompt` were generic one-liners that never referred to the data the worker actually attaches, so the injected material was ignored or only half used. Each prompt now names the blocks it receives: `CHARACTER PROFILE` (with its `Gender` field called out as authoritative), `EMOTIONAL STATE` (including the `A -> B -> C` progression form, and that the arc advances across replies rather than holding one mood), `INNER PERSONA BREAKTHROUGH`, and `USER EMOTIONAL STATE` on the user-side prompts. Only those clauses were added; the original opening sentence of each prompt is unchanged
- **Fixed: `sanitize_input()` corrupted every prompt that contained real prose** — it stripped double quotes, apostrophes and backslashes on every editor save, so `don't is right` was stored as `dont is right` and any prompt that quoted dialogue lost its quotation marks. A prompt written to forbid broken contractions was therefore modelling the exact error it banned, which is the likely origin of the broken contractions in earlier corpora. It now removes only `<` and `>`, which is what the bracket guard was for, and an authored `->` is held aside so an emotional arc written `A -> B -> C` survives the save instead of collapsing to `A - B - C`
- **Not a security boundary** — `sanitize_input()` is a shape guard for config values, not an HTML escaper. A value that is ever rendered into markup must be escaped at that sink with `html.escape()`; nothing in the codebase renders these values as HTML today
- **Regression guard** — the three prompts are checked to survive `sanitize_input()` unchanged, and the arc notation and contraction example are asserted present after a save round trip
- **Version bumped to v12.4** — the GUI version label in `generate.py`, the title of this README and this changelog

### v12.3
- **Fixed: every reply was dropped when `quality.cast_continuity` was on** — `score_conversation()` builds `default_weights` from the same opt-in toggles as `active_scoring_dimensions()`, but the cast set was never added to it. The composite loop then indexed `default_weights["cast_continuity"]`, raised `KeyError: 'cast_continuity'` inside the worker's scoring path, and `enqueue_quality_scoring()`'s exception handler turned that into a `judge_failed` drop — so with the toggle on, **100% of conversations were discarded**, and the judge itself was never at fault. `CAST_SCORING_DIMENSIONS` is now folded in beside the tic and roleplay sets, and `_weight()` uses a `.get()` fallback so a future opt-in dimension cannot resurrect the same crash
- **Fixed: the judge's `cast_continuity` score was parsed and then thrown away** — `score_conversation()` merged the judge's numbers for `LLM_DIMENSIONS` and `ROLEPLAY_LLM_DIMENSIONS`, but had no branch for `CAST_LLM_DIMENSIONS`. The dimension is LLM-only (deliberately no heuristic), so nothing else could fill it: the judge scored the cast, the value was dropped, and the dimension was emitted as `0`, silently dragging every composite down by its 0.10 weight. The cast scores are now merged like the roleplay ones
- **Fixed: the judge was not asked for `cast_continuity` on the default path** — `_call_logic_judge()` and `_call_logic_judge_once()` each rebuilt their fallback `expected_dims` as `LLM_DIMENSIONS + roleplay`, omitting the cast set. `expected_dims` doubles as the extraction ladder's `preferred_keys` and as the set of keys coerced into scores, so a reply the model *did* include the cast score in could have it stripped. Both now call one `_default_judge_dims()` helper that mirrors `_score_with_llm()`'s prompt exactly
- **Fixed: the Quality tab ignored the `tic_density` and `cast_continuity` toggles** — `_rebuild_quality_roleplay_layout()` gated its rebuild on `quality.roleplay_dimensions` alone, so switching on either other opt-in dimension mid-run left the summary labels and the Recent Scores table showing the old columns: the dimension was scored and stored but never displayed. The gate is now keyed on the whole active-dimension tuple, so it rebuilds when the set changes for any reason
- **Regression guard** — `tests/test_scene_cast.py` gained a headless `test_cast_dimension_is_scored()` that drives a stubbed judge with the toggle on and asserts no crash, no drop, a kept cast score, the cast dimension in the default judge dims, a weight for every active dimension, and that the key stays absent when the toggle is off. Both shipped defects were confirmed to fail this test before the fix

### v12.0
- **Scene Cast — characters join and leave a multi-character scene** — the "the world doesn't revolve around the player" feature. The **generator owns the cast**: the schedule is computed before any request is sent, the model is told who is present on each reply, and the model only *narrates* the entrances and exits. It never decides whether a character has left
- **A forgotten exit is cancelled, not assumed** — if the model never writes a scheduled departure, the exit is **cancelled** and the character stays legitimately present. Forcing the exit would make that character's very next legitimate line a continuity violation the generator itself invented. An un-narrated **arrival** is the opposite: it is forced to `present`, because being in the scene is the default and cannot corrupt the transcript. The asymmetry is deliberate
- **Hard continuity check, no LLM** — `detection.check_scene_continuity()` flags a character who has left (or has not arrived yet) speaking or acting: attributed quoted lines (including `Name:` script-style prefixes) plus a curated narration action-verb list. Quoted dialogue is blanked before the action match, so a character merely *mentioned* in someone else's line ("Where is Melody?") never flags. A hit sends the reply back to the same main API slot with a fix; once the fixes are exhausted the best-effort answer is kept, never dropped
- **Cache-safe by construction** — the cast note rides in the per-turn `depth0` note beside the persona/emotion blocks, so the system prompt never changes mid-conversation and a server's prefix cache stays warm. The note itself carries **no per-reply counter**, so two static replies produce byte-identical text
- **Opt-in Judge dimension `cast_continuity`** — the Judge reviews what code cannot: did the entrances and exits read as motivated and natural, and was an exited character brought back? **LLM-only, no heuristic** — there is no measurable proxy for "was that exit earned?", and the objective half of the question is already answered for free by the code check. Off by default
- **Metadata schema v7** — three new flat, type-stable keys on every record: `cast_schedule`, `cast_events` (including `exit_cancelled`, which is how you measure whether the model actually wrote its exits) and `quality_cast_continuity` (`-1.0` when off/unscored)
- **Configuration** — `prompts.scene_cast.{enabled,shape,min_present,max_churn,max_deferrals,placement,allow_cutaway,exit_guidance,arrival_guidance,cutaway_note}` (off by default), `detection.scene_continuity.{enabled,fixes,max_rounds}` and `quality.cast_continuity`. The Config Editor gains a **Scene Cast** panel in the Character Engine tab, a **Scene Continuity Check** panel in the Detection tab and a cast-continuity toggle in Quality Scoring; the main window gains a **Cast Drift** metric card, issue panel and graph series
- **Wiring** — `detection.py` (`check_scene_continuity()`, `find_attributed_speakers()`, `find_character_actions()`), `generation.py` (plan/state helpers, `_cast_presence_note()`, the retry branch, metadata v7, `DEFAULT_SCENE_CONTINUITY_FIX`), `generate.py` (config read + worker kwargs + metric card + issue panel), `config/config.yml`, `config_editor.py`, `app_state.py`, `dashboard.py`, `quality.py`, `docs/scene-cast.md`. Guarded by `tests/test_scene_cast.py`
